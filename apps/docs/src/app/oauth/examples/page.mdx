# OAuth 구현 예제

### 개요

이 섹션에서는 다양한 프레임워크와 아키텍처 패턴을 사용한 실전 OAuth 구현 예제를 제공합니다.
각 예제는 완전히 동작하는 코드와 함께 프론트엔드와 백엔드 구현을 모두 포함합니다.

### 시나리오별 선택 가이드

#### 시나리오 1: React + Spring Boot (BFF)

**언제 사용하나요?**
- 프로덕션 환경에서 최고 수준의 보안이 필요한 경우
- PKCE를 사용하여 Authorization Code 탈취를 방지하고 싶은 경우
- 토큰을 브라우저에 노출하지 않고 httpOnly 쿠키로 관리하고 싶은 경우

**특징**:
- BFF(Backend For Frontend) 패턴 사용
- 서버에서 PKCE 플로우 처리 (code_verifier 생성 및 전달)
- httpOnly 쿠키로 XSS 공격 방지
- **가장 안전한 구현 방식**

**플로우**:
```
사용자 → React (BFF 엔드포인트 호출) → Spring Boot (PKCE + OAuth 처리 + httpOnly 쿠키 설정) → 로그인 완료
```

#### 시나리오 2: Next.js + Spring Boot

**언제 사용하나요?**
- Next.js SSR/SSG 기능을 활용하는 경우
- 서버 측에서 완전한 OAuth 플로우 제어가 필요한 경우
- PKCE를 사용하여 보안을 강화하고 싶은 경우

**특징**:
- 프론트엔드는 Authorization Code만 획득
- 서버가 code_verifier를 전달해 Token 교환 담당
- 안전한 구현 방식

**플로우**:
```
사용자 → Next.js (code 획득) → Spring Boot (code_verifier로 token 교환 + JWT 발급) → 로그인 완료
```

#### 시나리오 3: React + Spring Boot (Kotlin)

**언제 사용하나요?**
- 백엔드가 있어 client_secret을 안전하게 보관할 수 있는 경우
- 자체 JWT로 앱 인증을 처리하는 SPA

**특징**:
- 프론트엔드는 인가 시작과 콜백 처리만 담당
- 서버가 client_secret으로 Token을 교환하고 자체 JWT 발급
- client_secret은 백엔드 환경 변수에만 보관

**플로우**:
```
사용자 → React (code 획득) → Spring Boot (token 교환 with client_secret + JWT 발급) → 로그인 완료
```

#### 시나리오 4: Vanilla JS + NestJS

**언제 사용하나요?**
- 백엔드가 있어 client_secret을 안전하게 보관할 수 있는 경우
- 프레임워크 없는 순수 JavaScript 프로젝트

**특징**:
- 프레임워크 없는 순수 JavaScript 구현
- client_secret 방식 사용
- 서버 측 세션 스토어 활용

**플로우**:
```
사용자 → Vanilla JS (code 획득) → NestJS (token 교환 with client_secret + 세션 생성) → 로그인 완료
```

### 공통 개념

모든 예제는 다음 공통 개념을 포함합니다.

#### Client ID & Client Secret

DataGSM에서 발급받은 인증 데이터입니다.
- **Client ID**: 프론트엔드에서 사용 가능
- **Client Secret**: **반드시 서버에서만 사용** (절대 프론트엔드 노출 금지)

#### Authorization Code

사용자 인증 후 발급되는 일회성 코드입니다 (5분 유효).

#### Access Token & Refresh Token

- **Access Token**: 사용자 리소스 접근용 (1시간 유효)
- **Refresh Token**: Access Token 갱신용 (30일 유효)

Refresh Token은 회전 방식입니다. 갱신할 때마다 새 Refresh Token이 발급되므로 응답의 새 값으로 바꿔 저장해야 합니다. 이전 토큰을 다시 쓰면 저장된 토큰까지 삭제되어 `invalid_grant`가 반환되고, 사용자는 다시 로그인해야 합니다. 같은 토큰으로 동시에 갱신하지 않도록 주의하세요.

#### 권한 범위 (scope)

인가 요청에는 필요한 scope를 명시합니다. 네 예제는 `datagsm:account_read datagsm:student_read`를 요청합니다. `datagsm:account_read`가 없으면 `/userinfo`가 403을 반환하고, `datagsm:student_read`가 없으면 `student`와 `teacher`가 `null`입니다. 요청하는 scope는 콘솔에서 클라이언트에 먼저 등록해야 하며, 등록하지 않으면 `invalid_scope` 오류가 발생합니다. 자세한 내용은 [권한 범위 레퍼런스](/oauth/scopes)를 참고하세요.

#### 콜백 처리

콜백에서는 `state`를 먼저 검증한 뒤 `error`를 확인합니다. 사용자가 동의를 거부하면 `code` 없이 `error=access_denied`와 `error_description`이 전달되므로 `code`가 없는 경우를 반드시 처리해야 합니다.

#### 요청 한도

`/v1/oauth/token`과 `/userinfo`는 OAuth 클라이언트 기준 분당 300회로 제한되며, 초과하면 429가 반환됩니다. 429는 인증 실패가 아니므로 세션을 지우지 말고 잠시 후 다시 시도합니다. `/userinfo`의 429에는 `Retry-After` 헤더가 포함됩니다.

#### 로그아웃

예제의 로그아웃은 앱의 세션이나 토큰만 정리합니다. DataGSM SSO 세션(8시간)이 남아 있으면 다시 로그인할 때 로그인 화면 없이 바로 콜백으로 돌아올 수 있습니다.

#### 리다이렉트 URI

OAuth 인증 후 사용자가 돌아올 URI입니다. DataGSM에 사전 등록되어야 하며, 등록값과 정확히 일치해야 합니다. 토큰 교환 요청에도 인가 요청과 같은 값을 보냅니다.

### 보안 권장사항

모든 예제에서 공통으로 적용해야 할 보안 권장사항입니다.

#### 1. PKCE 사용

PKCE는 공개 클라이언트와 기밀 클라이언트 모두에 권장합니다. `code_challenge_method`는 `S256`을 사용하세요. Authorization Code 탈취 공격을 효과적으로 방지합니다.

```typescript
// code_verifier 생성 (43-128자 랜덤 문자열)
const array = new Uint8Array(32);
crypto.getRandomValues(array);
const codeVerifier = base64UrlEncode(array);

// code_challenge 생성 (SHA-256 해시)
const encoder = new TextEncoder();
const data = encoder.encode(codeVerifier);
const hash = await crypto.subtle.digest('SHA-256', data);
const codeChallenge = base64UrlEncode(new Uint8Array(hash));
```

자세한 구현 방법은 [PKCE 가이드](/oauth/pkce)를 참고하세요.

#### 2. HTTPS 사용

프로덕션 환경에서는 반드시 HTTPS를 사용하세요.

#### 3. State 파라미터

CSRF 공격 방지를 위해 State 파라미터를 사용하세요.

#### 4. 토큰 저장

- **권장**: httpOnly 쿠키 (XSS 공격 방지)
- Access Token: 메모리 또는 sessionStorage
- Refresh Token: httpOnly 쿠키 또는 서버 세션
- **지양**: localStorage (XSS 공격에 취약)

#### 5. Client Secret 보호

client_secret은 백엔드 환경 변수로만 관리하고 프론트엔드 코드에 넣지 않습니다.

```bash
# 환경 변수로 관리
DATAGSM_CLIENT_SECRET=your-client-secret

# .gitignore에 추가
.env
.env.local
```

`REACT_APP_`, `NEXT_PUBLIC_`처럼 프론트엔드 번들에 포함되는 환경 변수에는 시크릿을 넣지 마세요.
